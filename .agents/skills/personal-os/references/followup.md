# 回填与每周主动跟进

## 固定约定

每个有待观察结果的决定、行动或假设创建独立的回填问题，关联案例。普通背景事实不自动创建无限追问。一个案例可以有近期与长期多个问题，短期完成只关闭对应问题。

有明确预计结果时间，按该时间安排检查；没有明确时间，建立事项后一周检查。明确暂无结果后，若用户没有给新时间，一周后再问；旧预计结果日期保留为背景，不继续拿旧日期覆盖这次周度间隔。无回复保持待回复，按一周节奏继续，不推断为暂无结果、拒绝或失败。

每晚由已部署的平台任务扫描到期项，集中主动发起交流；用户当天不先发言也应能运行。daily scan 与 weekly repeat 分开。具体时刻读取 settings；evening_time 为 null 时不要编造时刻或声称已启动调度。weekly_review 设置 merge_daily_review=true 时，该星期的晚间窗口和默认下次检查使用 weekly_review.time，以避免合并回顾后重复询问。

## 先查再问

到期时读取近期交流、正式记录、案例和可访问且已授权的工具。用户已提供结果时主动关联，先保存结果再更新跟进；工具显示“任务已完成”不能证明效果良好。需要个人体验或解释的部分仍需询问。

`due` 返回已知结果引用、上次答复状态与可选建议引用，供执行者先读近期进展。只问仍未知且会影响下一步判断的问题；能短答即可，允许跳过，不要求补交此前错过的访谈。问题已由自然交流回答时直接回填，避免重复追问。一次 partial 回答不自动关闭长期观察，也不因一条闲聊新建跟进任务。

询问带必要背景、原预期和一个明确问题。例如“上周你准备提前结束科研，看看第二天精力是否改善。后来实际尝试了吗？如果试过，精力和作业安排有什么变化？”允许自然回答有结果、部分结果、还没开始、暂无结果、改时间、暂停或停止，不要求用户填表。

把到期问题并入约十分钟的晚间交流；需要更多时间时明确剩余事项待问，不能标为已问或已完成。用户明确跳过就结束本次邀请，保留尚未解决的跟进。

## 字段与状态

followup 使用共用 Markdown 字段（见 memory.md），并包含：
- `case_id`、`question`。
- `expected_result_at`：预计可能有结果的日期/带时区时间或 null。
- `next_check_at`：下一次检查的带时区时间或 null。
- `cadence_days: 7`。
- `status`: active / paused / closed。
- `contact_state`: not_asked / awaiting_reply / replied。
- `answer_state`: unknown / no_result / partial / complete / unavailable。
- `last_asked_at`、`last_answered_at`：实际时刻或 null。
- `outcome_refs`：已正式保存的 outcome 记录 ID。
- `history`：保存每次处理的 `recorded_at`，以及实际送达或答复的时间、来源引用、动作和调度依据；实际交流时间未知时保持 null。

事项状态、联络状态、上次明确答复分别保存。发送重试不能把未确认发送算成已询问。扫描、发送、收到回复、归档是不同阶段。

## 工具使用

使用 `scripts/followups.py --help` 获取当前命令格式。所有写入经 records.py 统一校验与操作日志。

1. `create` 创建问题；期望日期只从真实约定填写。配置未完成时先生成可审阅草案，不自行启用提醒。
2. `due --root ROOT` 只读取到期问题，不发送、不推进时间、不写已提醒状态。`--at` 仅供只读模拟时刻。
3. 先核对真实平台任务 ID（自动任务场景）及执行回执；外部通知/主动消息实际发送并获得可核验标识后，用 `mark-asked` 写入 `--delivery-ref` 与稳定 `--check-id`。已知真实送达时间时传入 `--delivered-at`（带时区），不能用执行时间冒充。下一次默认在实际送达一周后的晚间。
4. `reply` 记录明确答复，使用 `--source-ref` 保留原消息引用；已知原消息时间时同时传入 `--answered-at`（带时区，必须有 source-ref）。先用 records.py 保存实际 outcome，再把 outcome-id 传入 partial/complete 回复。涉及多个写入阶段时逐一报告状态，失败只重试未完成部分。

实际交流时间未知时，脚本明确记载来源限制，并暂按处理时间安排一周后的检查。延迟导入按原消息时间计算，已经到期的事项交给下一次晚间批次处理，不重新延后一周。未来的送达/回复时间被拒绝；早于已知较新状态的旧消息返回 `needs_review`，不覆盖当前状态。人工核对后可将旧进展另存为历史证据。不能把 `--at` 或伪造来源时间当作修改系统时钟的入口。

`no_result`：保留已有结果与历史，设置下次检查。`partial`：追加结果但继续观察。`complete`：只关闭本问题。`unavailable`：未知作为有效终点，不造结论。`pause`：有新时间则到时恢复，无时间则暂停等待用户；`stop`：停止跟进，不把取消改写为成功结果。

没有回复时无需调用 reply；已确认发送时的 next_check_at 控制每周重问。发送失败保持待发/到期，处理投递失败时避免反复骚扰。不能仅写一个文件就宣称已经建立平台调度。

## 回填之后

保留原来的预期、本人判断、AI 判断以及实际过程。分别更新每个假设的支持、反驳或不确定证据；用户认可与证据支持分别记录。关注副作用、反例及长期影响，失败或无改善同样是有效结果。需要时更新当前概况、经验案例和报告的纠错说明。

自发交流也是回填入口：用户提到新进展即检索旧问题，明确匹配则自动补入，有多种可能才询问。不要为了等定时检查而丢下已有结果。
